# 客户端设计

把用户的客户端需求转成可实现、可验收的界面与交互方案。默认聚焦桌面端；平台和窗口形态从用户上下文确定，不能把 Mac 客户端自动解释为 iOS。

## 先确定边界

从用户消息、参考图和现有项目中确认：目标平台、主窗口/菜单栏/托盘形态、核心操作、现有数据来源、已确定的技术栈。已经明确的信息不重复询问。

- 用户说“简单实现”，先做完成核心操作所需的最小界面，不扩成仪表盘、多页面后台或完整会话工作台。
- 用户明确 Rust + React 时，将其作为实现约束；不改选 SwiftUI、Electron 等技术。
- 截图用于理解层级、密度、留白和交互，不意味着照搬品牌、无关模块或截图里的假状态。
- 本机服务管理和远程设备控制是不同产品职责。只在两者影响入口和权限且上下文仍不清楚时，询问这个产品决策。
- 只有影响产品结果的缺失信息才需要提问；其他细节采用合理默认并说明。此技能不新增审批流程，不重复请求已获得的授权。

## 从真实能力设计交互

先检查后端或已有客户端暴露的能力，再决定哪些操作可用。纯概念设计可列出接口需求，但要标明尚未实现。

为核心流程描述“入口 → 操作 → 等待 → 结果/失败后的下一步”。按实际风险覆盖相关状态，不为每个小改动穷举所有状态。

- 首次使用和空状态应告诉用户下一步能做什么。
- 请求处理中避免重复提交；超时不伪装成已取消或未执行。
- 状态面板中区分本地进程运行、网络可达、设备已授权、设备在线；没有来源的最近在线时间和统计不要编造。
- 停止服务、撤销设备等有副作用的动作说明具体影响。普通刷新、打开面板不堆叠确认框。
- 未支持的能力隐藏或明确禁用；不要让漂亮的按钮实际无效。
- 错误提示包含可执行的下一步；令牌、密钥、完整内部堆栈不属于普通状态文案。

## 布局与视觉

先安排主操作和信息层级，再处理样式。沿用项目已有设计语言；没有约定时采用平台习惯、清晰字体层级、有限的强调色与统一间距。

菜单栏/托盘界面优先紧凑、可扫描、有限高度和必要的滚动；不要机械缩小完整网页。主窗口按内容复杂度选择导航方式，不默认加侧栏。确定最小可用尺寸、长名称换行/截断、弹窗定位、浅深色和键盘焦点行为。

状态不要只靠颜色表达。图标按钮有可理解的名称，文本和控件对比度可读。实现技术可以是 React，但产品文案不暴露 IPC、Rust crate 等无助于用户操作的细节。

## 交付与验证

按任务规模交付，不机械制造文档：

- 小调整：直接说明布局/状态差异和验收点。
- 新页面或多状态流程：用项目现有设计文档承载范围、布局、交互状态、组件/数据映射和验收标准。需要完整交接时参考 [设计交接](references/design-handoff.md)。
- 用户请求可交互原型时才增加原型实现；示例数据明确标注，不当成真实连接或功能完成的证据。

已有可运行界面时，查看实际渲染并检查关键尺寸、空/错误状态、弹窗和文字溢出。未渲染的方案标为设计方案，不宣称已视觉验收。

设计进入开发时，沿用交接中的范围和状态契约。用户已要求端到端实现则继续实现，不因为本技能产生额外停顿；需要开发指导且可用时使用 `client-development`，否则直接沿用项目流程。
