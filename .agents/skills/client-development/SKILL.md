# 客户端开发

将已有需求或设计实现为可运行的桌面客户端，交付实际功能、验证证据和可定位的构建产物。

## 技术选择与范围

- 新建 Rust + React 桌面客户端，默认使用 **Tauri 2 + Rust + React + TypeScript + Vite**。如果用户或现有项目明确采用其他方案，遵循该约束，不擅自迁移。
- 沿用已有依赖管理器、UI 组件和状态管理方案；小客户端不为了架构完整额外加入全局状态库、路由系统或远程服务。
- 先确认目标操作系统和形态。Mac 不等于 iOS，菜单栏弹窗不等于完整工作台。
- 有设计交接就读取；没有但需求已足够明确时可直接实现最小界面，不强制先运行另一技能或新增设计审批。
- 遵循已有项目流程和本轮授权。用户明确要求变更技术栈时，同步实现计划并执行该变更；只有尚未确定的产品范围或必要权限才需询问。

## 建立端到端边界

先读当前入口、依赖、系统集成和后端契约，避免只替换页面而留下旧构建链。Tauri 项目实现前按涉及部分阅读 [Rust/React 桌面契约](references/tauri-react-contracts.md)。

职责默认如下，可依据已有架构调整：

- **React/TypeScript**：视图、交互、表单、显示状态与即时校验。
- **Rust/Tauri**：受限命令接口、进程与资源所有权、系统能力、凭据访问、生命周期。
- **已有 daemon/服务**：继续拥有其业务状态和权限规则。复用已验证接口，不在 UI 中再做一套授权或状态机。

进程内 Rust API 和独立 daemon 都是可选方案。已有稳定 daemon 时可通过受控 sidecar/IPC 复用；没有独立进程需求时，不为套用模板额外引入一个进程。

## 实现顺序

按依赖推进：先确定命令/事件契约并跑通最小调用，再连接主操作与状态，之后完善托盘/窗口、系统设置与打包。可并行的模块遵循项目协作规则，但本技能不额外要求必须使用多代理。

- 保留用户需要的行为，界面必须调用真实实现；预览/测试适配器与实际运行路径明确分开。
- 异步操作有超时、错误和过期响应处理。变更重试遵循服务幂等语义，不能把超时当作“未执行”。
- 系统能力失败要反馈给界面；登录启动、权限、网络连接和设备状态显示实际结果。
- 旧实现的入口、打包脚本、说明与测试在迁移时一起更新。若需暂留旧代码，应标明用途并避免继续打包；不删除与迁移无关的用户文件。
- 新增文件放在已有布局中；新项目才考虑 `src/` + `src-tauri/`，不要重排整个仓库以迎合模板。

## 验证与交付

使用项目实际命令，不假设某个测试框架已安装：

1. 前端类型检查与生产构建；Rust 格式、Clippy 和相关测试。
2. 对关键交互、通信和生命周期补行为测试。优先覆盖重复启动、旧响应、错误恢复、关闭与退出等真实风险；不为颜色/文案的小改动制造镜像测试。
3. 运行真实界面检查布局、控件状态、空/错误状态和弹层。可用浏览器验证 React 视觉；Tauri 系统功能还需原生运行验证，浏览器通过不能代替托盘/进程/登录项测试。
4. 按目标平台构建应用包，核对前端资源、sidecar 路径、可执行权限和签名状态。构建成功不等于已经启动验证。

已有授权范围内持续修复失败，直到可交付。若外部环境或必要权限阻止验证，保留已完成结果并明确具体未验证项，不虚报通过。

最终报告技术栈、主要功能、验证结果、应用产物位置和实质限制。测试数据截图标注预览；本地签名不宣称公证或商店可分发。安装、启用登录项、签名凭据和发布操作遵循已有授权，不把开发请求扩大成额外系统变更。
