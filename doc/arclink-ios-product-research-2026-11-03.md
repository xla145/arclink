# ArcLink iOS 调研与下一阶段优化方向

调研日期：2026-11-03。范围：手机端产品定位、竞品公开能力、当前源码差距与建议实施顺序。

**建议方向：围绕「需要我处理的事」组织 iOS。用户收到提醒，理解问题，做出决定，确认 Mac 已接收，然后收起手机。**

手机保留三项核心能力：处理待办、查看结果、简短交代任务。Mac 承担执行、配置和复杂检查。第一版聚焦单人使用、已配对且保持在线的 Mac、ArcLink 实际管理的 Codex 会话。

## 1. 研究方法与结论边界

- 阅读 Happy、Orca、Claude Code Remote Control、GitHub Mobile/Copilot 和 Termius 的官方页面或维护者文档，文末给出来源。
- 检查 ArcLink iOS 导航、审批、会话驱动、持久化及项目 README，并对照 Mac 端字节转发契约。
- 本轮没有安装竞品做实机对照，没有访谈用户，也没有测量各产品的推送延迟、耗电、稳定性或转化率。竞品能力表示「官方明确描述」，不等于本次验证通过。
- 建议的差异化属于待验证产品假设，不能宣称市场独有。文中的目标指标是建议验收值，没有现有数据基线。
- 沿用本次会话不创建 Trellis 任务的选择；本文是调研建议，不是已批准的开发计划。本轮未修改业务代码。

## 2. 竞品说明了什么

| 产品 | 官方明确描述的手机相关能力 | 核心使用方式 | ArcLink 的启示 |
| --- | --- | --- | --- |
| Happy | 扫码配对；电脑运行 Agent；手机发消息和图片、回答权限请求、切模型、停止 turn、新建会话、看文件与 Git 变更；多 Agent 与端到端加密 [S1] | 在手机延续电脑上的 Agent 工作 | 多模型、加密、扫码、聊天同步均不能单独作为差异化 |
| Orca Mobile | 跨主机汇总 worktree；展示 working/done/waiting on input；短回复、问答/权限、图文/语音；完成推送；还包含文件树、终端、Git 操作、账户切换 [S2] | 监控运行中的工作，并在手机解除阻塞 | 与目标最接近；「待处理、快回复、多设备汇总」已有竞争。可以尝试更少入口、更清楚的决策内容 |
| Claude Code Remote Control | 连接本机 Claude Code；终端、网页、手机同步会话与进度；支持附件；本机环境持续可用，机器及进程必须保持运行 [S4] | 原生会话连续性 | 单用 Claude 的用户已有官方路径；第三方需要在跨 Agent 一致体验、注意力管理上创造价值 |
| GitHub Mobile / Copilot | 在移动端提问、委派工作、参与 issue/PR 工作流；官方文档描述跨端会话与不同执行环境，受套餐和策略约束 [S5] | 围绕仓库任务与成果协作 | 可借鉴「任务 → 产出 → 反馈」；不需要为本地 Mac 产品照搬完整仓库管理 |
| Termius | iOS/Android SSH、主机同步、终端、命令及团队基础设施管理 [S6] | 远程深入操作 | 作为替代方案参考；完整终端对排障有用，但不适合成为所有用户的默认路径 |

**需要修正的先前判断：**「手机有个待办箱」本身不足以拉开差距。Orca 已经公开提供等待输入、跨主机聚合和通知，Happy 也有权限回答和推送能力。更有价值的假设是：**ArcLink 能否把多数介入压缩成一张可理解、可操作、可追踪结果的卡片，使用户少翻会话、少做配置、少受打扰。**

还要区分两件事：Orca 的通知文档明确讨论 unread 与 working→idle，且不同结构化会话路径的通知行为不同 [S3]。这说明「有新消息」「本轮结束」「需要你决定」「整个任务完成」不是同一个状态，ArcLink 应明确区分。

Happy 的旧 CLI 已知问题文档提到，长会话压缩缺少手机端提示可能让用户对上下文变化感到意外 [S8]。这是旧 CLI 的公开问题，不能推断当前桌面产品仍有同一缺陷；但提醒我们，简化界面不能隐藏影响判断的上下文变化。

## 3. 当前 ArcLink 的真实起点

以下是源码静态审查结果，不代表已经完成当前版本真机验收。

| 现状 | 证据 | 对新方向的影响 |
| --- | --- | --- |
| 首页以设备、Agent、项目、会话为主；审批是铃铛次级入口 | `HomeView.swift`、`AgentBridgeApp.swift` [L1] | 用户需要先找工作，再找待处理事项；应把待处理提升为第一入口 |
| 已有 Codex 图文对话、命令/文件审批与中断、恢复等基础 | `CodexChatSession.swift`、iOS README [L2][L4] | 能复用现有能力，先做一个真实闭环，不必重建全部聊天 |
| 当前结构化服务器请求只接受命令执行及文件修改审批，其他请求明确拒绝 | `receiveServerRequest` [L2] | 「回答问题/选择方案」需要新增协议支持，换卡片样式不会自动获得能力 |
| 审批原生 ID 与可写驱动保存在手机内存；处理审批依赖 `chats` 和 `approvalRequests` | `AppModel.swift`、`CodexChatSession.swift` [L2][L3] | 本地保存了审批行，不代表 App 被杀后仍能正确回复原请求 |
| 设置存在通知开关；README 明确没有 APNs/后台保活，挂起不承诺持续连接 | `SettingsViews.swift`、iOS README [L4] | 还不能承诺「锁屏后有事叫我」；需要 Mac 主动记录事件和通知路径 |
| Mac 当前以透明字节转发为基础，聊天语义由手机负责 | host contract、`process.rs` [L5] | 持久待办需要一个 Mac 侧的会话事件层；不能只监听手机收到的消息 |
| 桌面来源会话在当前 iOS 模型里只读 | `SessionItem.isReadOnly` [L3] | 读到 Mac 历史不等于接管 Mac 上任意已有会话；首版必须明确支持哪些来源 |
| 设备工作区隔离；当前审批数基于选中设备 | `AppModel.swift` [L3] | 可以保留隔离，同时新增只读聚合视图；任何操作仍须明确目标设备/会话 |
| 已有断线恢复与不自动重发保护，但 App 被杀、Mac 重启有明确边界 | iOS README [L4] | 不能把「能重连」描述成「任何重启都无缝续跑」 |
| 模型实时列表刚完成源码修改；会话模型同步尚未修复 | 本次会话变更、`ChatSessionOptions` [L3] | 这是应优先修复的可信度问题；把设置藏起来不能掩盖模型不一致 |

最关键的产品差距是：**目前能在手机打开时处理部分会话；目标是手机不在场时，系统也知道有什么在等用户。**

## 4. 产品定位与功能边界

目标用户先限定为：在 Mac 上使用 Agent 开发、会短暂离开工位、希望任务不要因等待一个决定而停住的个人开发者。

优先满足三种场景：

1. **离开工位后解除阻塞。** 收到提醒，理解请求，批准或回答，确认继续。
2. **碎片时间查看成果。** 看摘要、截图或关键验证，补充一句修改要求，或留到 Mac 处理。
3. **临时交代一件事。** 给已有任务发文字或图片；新任务复用最近明确选择的项目与配置，并显示执行目标。

三个产品取舍：

- 不要求用户把 Agent 的每一步都当作自己的待办；只有需要人的介入才计数。
- 不把长聊天记录作为理解请求的唯一途径；卡片先解释原因，详情提供原始证据。
- 不靠扩大自动授权换取「少点击」；减少重复提问和无效通知，保留必要的判断。

## 5. 推荐的信息结构

手机只保留两个主要入口：**待处理**与**任务**。设置使用右上角入口；「交代任务」作为轻量按钮。配对仍是首次使用流程。

```text
待处理（默认首页）
  需要你决定：批准、回答、选择、可处理的阻塞
  正在进行：一行概况，可展开，不计待办数
  最近完成：结果摘要；默认不要求点确认

任务
  进行中 / 已结束，搜索与项目筛选
  任务详情：当前状态、结果、补充一句、停止、上下文
  更多：完整会话、日志、终端、高级配置

设置
  设备配对、连接、通知偏好、外观
```

多设备和多 Agent 默认聚合已经支持的活跃事项；卡片保留来源。无需每次先切设备/Agent。第一版可以只接单台 Mac 的真实 Codex 事件，聚合视图应随着第二个真实来源接入验证，不能用假数据宣称已支持全部 Agent。

离线空状态必须与「没有待办」区分：例如「上次同步没有待处理事项 · Mac 当前离线」，避免给出错误的安心感。

## 6. 待办应如何设计

建议逐步支持四种需要人介入的事项：

| 类型 | 卡片必须说明什么 | 主要操作 | 首版范围 |
| --- | --- | --- | --- |
| 请求批准 | 要做什么、原因、目标/影响范围、原始命令或差异入口 | 允许这次 / 拒绝 | 优先复用现有命令和文件审批 |
| 请求回答 | 具体问题、有限选项及差别；有依据时展示推荐理由 | 选择 / 简短回答 | 第二步补原生结构化问答 |
| 执行受阻 | 真实阻塞原因，以及用户现在能做的下一步 | 补充信息 / 经核实后重试 / 回 Mac 处理 | 只接可信事件；不从任意错误文字生成按钮 |
| 请求验收 | 交付物、验证证据、未验证内容、需要确认什么 | 接受结果 / 提出修改 / 留到 Mac | 只有任务明确要求验收才进入待办 |

「已完成」默认进入结果区，不新增确认负担。一次 turn 完成只表示 Agent 本轮结束，不能自动标记用户目标已完成。

卡片示例（设计示意，非现有实现）：

> **登录修复 · 需要你选择**  
> 项目 A · MacBook · Codex  
> 登录过期后，有两种恢复方式：自动重试一次，或直接要求重新登录。  
> 建议重试一次；第二次失败再提示登录。  
> **自动重试一次**　**直接重新登录**  
> 查看上下文

这里的推荐必须有 Agent 或确定性规则提供的依据。涉及权限时，摘要不能代替真实命令、参数、目标目录与差异；无法提供足够信息就明确引导到 Mac。

交互状态至少区分：待处理、发送中、Mac 已接收、已解决、已失效、结果待核实。收到请求的「确认接收」不等于 Agent 已继续执行。网络断开时保留待核实状态，不能自动再次发送决定。

「稍后」只影响提醒，不表示任务继续；「回 Mac 处理」明确保留阻塞状态。不要对不同作用范围的审批默认提供一键全部允许。

## 7. 真正值得投入的差异化假设

| 假设 | 对用户的价值 | 怎样判断是否成立 |
| --- | --- | --- |
| 事项优先的首页比会话/项目优先更适合短时手机操作 | 不必逐个查会话 | 同一批场景下，定位与处理时间更短，理解错误不增加 |
| 卡片提供充分而简短的上下文 | 少翻长对话，也敢做决定 | 大部分事项可在卡片和一层详情内正确完成 |
| 只有人能解决的问题才提醒 | 通知值得打开 | 无需操作却被提醒的比例低；用户愿意持续开启通知 |
| 同一任务在 Mac 和手机有一致状态 | 处理后能放心收起手机 | 旧审批不复活；另一端处理后卡片失效；不因断线重复操作 |
| 默认继承会话与执行配置 | 用户不需每次重新设置 | 实际模型/项目与显示一致；高级配置使用频率降低但可找回 |

这些方向已有竞品部分覆盖。潜在优势来自整条流程的完成质量，尚没有证据支持「唯一」「最简单」等市场表述。

## 8. 开发顺序与每阶段验收

不在尚未做技术验证时承诺工期。以下按依赖与产出排序。

| 阶段 | 具体交付 | 完成标准 |
| --- | --- | --- |
| A：可信度与接入边界 | 修正会话模型显示/继承；验证已改的模型列表；区分可控制会话和只读历史；梳理哪些 Mac 发起会话可产生真实事件 | 同一会话显示与实际使用一致；无法控制的来源明确标注；不创建假审批 |
| B：Mac 持久待办基础 | 一个受支持 Codex 会话的事件采集、事项存储、稳定身份、状态查询和决定回复；手机重开可拉取待办 | 手机挂起/被杀时 Mac 仍保存请求；重新打开能恢复事项；原请求消失就失效；重复点击不重复执行 |
| C：待处理首页与通知闭环 | 卡片首页、详情、状态回执、深链接、APNs 可见提醒、前台补拉、过期校验；通知按事项合并 | 真机锁屏触发请求 → 收到提醒 → 打开对应卡片 → 决定送达 → 观察到继续；断网和另一端先处理也能正确收敛 |
| D：从审批扩展到问题与成果 | 原生问答适配；可信阻塞原因；结果摘要/截图；简短反馈；同一事项跟进 | 不支持的请求不伪装为可回答；完成结果不强制确认；修改意见能回到原任务 |
| E：扩大范围 | 第二种 Agent、跨 Mac 聚合、快捷新任务；基于用户反馈决定是否加语音/小组件 | 复用相同待办规则；操作不串设备；新增能力不增加默认首页复杂度 |

阶段 B 可以先做内部验证界面；阶段 C 才形成「手机放下也能收到请求」的对外闭环。首页视觉原型可以提前验证，但不能把只改首页当作产品目标完成。

**建议下一批工作项，按顺序：**

1. 画出“Mac 开始任务 → 手机离开 → 产生请求 → 手机上处理 → 继续执行”的真实事件路径，明确受支持会话来源。
2. 补齐模型同步和来源标签，避免继续累积状态不一致。
3. 用一条真实 Codex 审批验证 Mac 侧记录、App 被杀后恢复和决定回执。
4. 制作三种卡片原型：批准、选择、结果；用现有项目页做对照。
5. 接入可见推送和卡片深链接，同时完成重复、迟到与已处理事件的收敛。
6. 上线待处理首页，收起项目、终端与模型配置入口。
7. 扩展原生问答和结果反馈；再评估第二 Agent 与多设备聚合。

这批工作不包含移动端完整文件编辑器、Git 分支管理、复杂模型调参、终端增强、Agent 市场或自动多 Agent 编排。语音和小组件也应排在核心闭环验证之后。

## 9. 影响产品承诺的技术约束

**手机不能成为待办的唯一发现者。** 当前会话驱动在 iOS 解读原生请求。建议在 Mac 增加受控的会话事件/协调层，并沿用现有配对授权及传输；具体采用原生协议适配或受支持 hook 需要单独技术验证。结构化协议能提供的请求可以成为可操作事项，日志推测只能作为提示，不能伪造可回复请求。

**接入所有 Mac 会话是独立问题。** 能读取 Codex/Claude 历史不代表能接管它们正在运行的请求。第一版只承诺经 ArcLink 管理或明确接入的会话；若用户主要在现有原生桌面会话工作，则验证该来源的可接入性是阶段 A 的首要门槛，不能用“改到手机新建”替代需求。

**通知与数据同步分工。** Apple 明确表示后台静默通知是低优先级且不保证投递，不能拿它持续保活 [S7]。需要用户介入的事项使用可见提醒；通知仅作提示，Mac 的事项记录才是依据。打开 App 再查询最新状态，即使漏推送也能看到未处理事项。可见推送同样受用户设置、专注模式和网络影响，不承诺绝对即时。

**需要一个受信任的推送提供方。** iroh 直连/中继不能直接替代 APNs。建议自有推送服务仅接收路由所需标识与泛化提醒，不放代码或命令正文；正文打开 App 后走授权链路获取。APNs 提供方凭据留在服务端，不能打包进手机或分发给所有 Mac。推送所需服务意味着产品对“完全不依赖服务器”的表述也应相应调整。

**事项要可对账。** 建议身份至少关联设备、会话/进程代次、原生请求 ID 和版本；支持查询当前状态与重复决定去重。Mac 重启后无法恢复的请求必须标记失效或待核实，不能重放旧批准。传输层成功只证明投递阶段，继续执行要另有事件依据。完整技术契约留待实现设计，本文不宣称现有协议已具备这些能力。

**一份决定只能有一个有效执行入口。** 现在已有输入租约与不自动重发保护；加入 Mac 侧协调不能绕开这些保护，更不能让手机与 Mac 同时竞争写入。同一事项在其他端先解决后，手机只展示最新结果。

## 10. 通知规则与轻量验收

建议默认：等待批准/明确问题即时提醒；任务无法自行恢复且用户能处理的阻塞提醒；普通完成放结果区，可选择汇总通知；工具步骤与 token 流不通知。相同事项只维护一个提醒，macOS/手机任一端处理后同步状态，前台正在查看的事项减少重复通知。

所有通知点击后先核对状态。已失效时显示“已在 Mac 处理”或“请求已结束”，不继续展示旧批准按钮。拒绝通知权限后，仍允许用户主动进入待处理；明确说明不会收到系统提醒。

首轮建议招募 5–8 名经常在 Mac 使用 Agent 的开发者，做当前界面与卡片原型对照；顺序交叉安排，避免学习偏差。然后做一周真实使用试点。本轮尚未实施这些测试。

| 需要验证 | 场景/指标 | 建议初始目标（非现有实测） |
| --- | --- | --- |
| 能快速理解 | 问题、影响和下一步的复述正确率 | 至少 80%，关键权限范围不得误读 |
| 能快速处理 | 从打开事项到提交有效决定 | 简单事项中位数不超过 30 秒，并优于当前路径 |
| 少翻上下文 | 不进入完整聊天即可正确处理的比例 | 至少 70%；复杂事项允许回 Mac |
| 少打扰 | 抽样判断“收到提醒但无需人做任何事” | 不超过 10%，并收集误提醒原因 |
| 状态可信 | 重复点击、断线、App 被杀、另一端先处理、Mac 重启 | 测试中无重复执行，无过期批准；不确定状态可见 |
| 真正解阻塞 | 有效决定到观察到 Agent 继续的耗时 | 单独记录分位数与失败原因；先建立基线，不把 APNs 提交成功算送达 |

再问用户一个决定投入方向的问题：“你离开电脑后，最常想做的是批准、回答、验收，还是主动发起任务？” 用实际频次决定后续排序，而不是按功能数量决定。

## 11. 最终建议

下一阶段的产品目标可以写成：

> 当 Mac 上已接入的 Agent 需要我决定时，ArcLink 在手机上准确告诉我原因和选项；我处理一次，就能确认它继续工作。平时不需要打开应用盯进度。

最先做的是一个真实 Codex 会话的持久待办与通知闭环，并修复基础状态不一致。界面围绕待处理收敛，原有聊天和终端作为深层上下文保留。完成这一闭环后，再用用户数据决定问答、验收、新任务、多 Agent 哪一项值得扩展。
